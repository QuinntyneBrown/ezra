# L2 - Detailed Requirements

## L2-001: Distributed as a .NET tool
**Traces to:** L1-001

Ezra shall be packed as a NuGet package configured as a .NET tool whose command name is `ezra`, targeting the current .NET LTS runtime.

**Acceptance Criteria:**
1. Given the Ezra package, when the user runs `dotnet tool install --global Ezra`, then the `ezra` command is available on the PATH.
2. Given the Ezra package, when the user runs `dotnet tool install --local Ezra` in a folder with a tool manifest, then `dotnet ezra` runs Ezra.
3. Given an installed older version, when the user runs `dotnet tool update --global Ezra`, then `ezra --version` reports the new version.
4. Given Ezra is installed, when the user runs `ezra --version`, then the package version is printed and the exit code is 0.

---

## L2-002: Runs on Windows, macOS and Linux
**Traces to:** L1-001

Ezra shall use no platform-specific APIs, shall build all file paths with platform-neutral path APIs, and its acceptance tests shall run in CI on Windows, macOS and Linux.

**Acceptance Criteria:**
1. Given CI runs on Windows, macOS and Linux, when the acceptance test suite runs, then all tests pass on all three.
2. Given any command that writes files, when it runs on Windows, then paths use the Windows separator and on macOS/Linux the `/` separator.
3. Given text files Ezra generates, when they are written, then they are UTF-8 without BOM and use `\n` line endings on every platform.

---

## L2-003: Root command and nested subcommands
**Traces to:** L1-002

The `ezra` root command shall host top-level commands (for example `scaffold`), each of which may host further subcommands to any depth. Commands, options and arguments shall be parsed with a single shared command-line parsing library.

**Acceptance Criteria:**
1. Given a tool that registers command `scaffold` with subcommand `x`, when the user runs `ezra scaffold x`, then the handler for `x` runs.
2. Given the user runs `ezra` with no arguments, then the list of top-level commands with one-line descriptions is printed and the exit code is 0.
3. Given the user runs an unknown command `ezra nope`, then an error naming `nope` and the closest matching command (if any) is written to stderr and the exit code is 1.

---

## L2-004: Help at every level
**Traces to:** L1-002

Every command and subcommand shall provide help generated from its declared description, arguments and options.

**Acceptance Criteria:**
1. Given any command path `P`, when the user runs `ezra P --help` (or `-h`), then usage, description, arguments, options and subcommands of `P` are printed and the exit code is 0.
2. Given a command declares an option with a default value, when its help is shown, then the default value is displayed.
3. Given a command declares an option with allowed values, when its help is shown, then the allowed values are listed.

---

## L2-005: Tool module contract
**Traces to:** L1-003

Each tool shall be its own project and assembly named `Ezra.<Tool>` (for example `Ezra.Scaffold`) that implements one shared module contract defined in an `Ezra.Abstractions` project. The contract lets a module contribute its commands and register its services with the host. Modules shall depend only on `Ezra.Abstractions` (and their own dependencies), never on each other or on the root host.

**Acceptance Criteria:**
1. Given a new module project implementing the contract, when it is registered with the host, then its commands appear in `ezra --help` with no change to any other module.
2. Given two modules, when each registers services, then each module's command handlers resolve their own services through dependency injection.
3. Given a module that declares a top-level command name already used by another module, when Ezra starts, then it fails with an error naming both modules and the duplicate command, and the exit code is 1.

---

## L2-006: Orchestration across tools
**Traces to:** L1-003

A command in one module shall be able to invoke a capability of another module only through a service interface published in `Ezra.Abstractions` (or a module-owned contracts package), never by referencing another module's implementation or by spawning `ezra` as a child process.

**Acceptance Criteria:**
1. Given module A depends on a capability that module B implements behind a published interface, when A's command runs, then B's implementation is resolved and invoked in-process.
2. Given module B is not registered, when A's command that needs B runs, then Ezra fails with an error naming the missing capability and the exit code is 1.

---

## L2-007: Consistent exit codes
**Traces to:** L1-004

All commands shall use the same exit codes: `0` success, `1` usage or validation error, `2` runtime failure (for example an I/O error), `130` cancelled by Ctrl+C.

**Acceptance Criteria:**
1. Given a command completes, then the exit code is 0.
2. Given a required argument is missing or an option value is invalid, then the exit code is 1 and no files are written.
3. Given an unhandled exception occurs in a handler, then a one-line error is written to stderr, the stack trace is shown only with `--verbose`, and the exit code is 2.
4. Given the user presses Ctrl+C during a command, then the command stops at the next cancellation check and the exit code is 130.

---

## L2-008: Output and verbosity
**Traces to:** L1-004

Normal output shall go to stdout and errors to stderr. Every command shall accept the global options `--verbose` (detailed diagnostic output) and `--quiet` (errors only). Colour shall be disabled when output is redirected or when the `NO_COLOR` environment variable is set.

**Acceptance Criteria:**
1. Given any command, when run with `--quiet` and it succeeds, then nothing is written to stdout.
2. Given any command, when run with `--verbose`, then each significant step (for example each file written) is logged.
3. Given stdout is redirected to a file or `NO_COLOR` is set, when a command runs, then the output contains no ANSI escape sequences.
4. Given both `--verbose` and `--quiet` are passed, then a validation error is reported and the exit code is 1.

---

## L2-009: `ezra scaffold` command
**Traces to:** L1-005

The `Ezra.Scaffold` module shall provide `ezra scaffold <name> [--backend <backend>] [--output <dir>] [--skills-source <dir>] [--force]`. It creates the folder `<output>/<name>` (output defaults to the current directory). `--backend` accepts `node` in this release.

**Acceptance Criteria:**
1. Given an empty current directory, when the user runs `ezra scaffold shelfie --backend node`, then a folder `shelfie` is created containing `AGENTS.md`, `CLAUDE.md`, `.agents/skills/` and `.claude/skills/`, and the exit code is 0.
2. Given `--output /tmp/work`, when the user runs `ezra scaffold shelfie --backend node --output /tmp/work`, then the project is created at `/tmp/work/shelfie`.
3. Given `--backend rust`, when the command runs, then an error lists the allowed values (`node`), the exit code is 1 and nothing is written.
4. Given the command succeeds, then a summary prints the project path and the number of skills copied.

---

## L2-010: Generated AGENTS.md
**Traces to:** L1-005

The scaffolded `AGENTS.md` shall start with a `# <name>` heading, include a `## Tech stack` section naming the chosen backend (`Node.js` for `node`), and include the standard, project-independent engineering rules: "Scope, Simplicity, and Zero-Waste Engineering", "Incremental Implementation and ATDD" and "Never write architecture tests". The template shall ship embedded in the `Ezra.Scaffold` assembly.

**Acceptance Criteria:**
1. Given `ezra scaffold shelfie --backend node`, when `shelfie/AGENTS.md` is read, then its first line is `# shelfie`.
2. Given `--backend node`, when `AGENTS.md` is read, then its Tech stack section states the backend is Node.js.
3. Given any scaffold, when `AGENTS.md` is read, then it contains the three standard rule sections verbatim from the embedded template.

---

## L2-011: Generated CLAUDE.md
**Traces to:** L1-005

The scaffolded `CLAUDE.md` shall contain only a pointer to `AGENTS.md`.

**Acceptance Criteria:**
1. Given any scaffold, when `CLAUDE.md` is read, then its entire content is `@AGENTS.md` followed by a newline.

---

## L2-012: Copy locally installed skills
**Traces to:** L1-005

The scaffold shall copy every skill (a folder containing a `SKILL.md`) from the skills source into both `.agents/skills/` and `.claude/skills/` of the new project, preserving each skill's folder structure and file contents. The default skills source is the user-level skills folder `~/.claude/skills` (`%USERPROFILE%\.claude\skills` on Windows); `--skills-source` overrides it.

**Acceptance Criteria:**
1. Given the skills source contains skills `a` (with nested folders) and `b`, when scaffolding, then `.agents/skills/a`, `.agents/skills/b`, `.claude/skills/a` and `.claude/skills/b` exist and are byte-identical to the source, including nested files.
2. Given a folder in the skills source without a `SKILL.md`, when scaffolding, then it is not copied.
3. Given the skills source folder does not exist or contains no skills, when scaffolding, then the project is still created, a warning states that no skills were found at the resolved path, and the exit code is 0.
4. Given `--skills-source <dir>`, when scaffolding, then skills are copied from `<dir>` and not from the default location.

---

## L2-013: Project name validation
**Traces to:** L1-006

`<name>` shall be 1–100 characters of letters, digits, `-`, `_` and `.`, shall not start with `.` or `-`, and shall not be a reserved device name on Windows (for example `CON`, `NUL`).

**Acceptance Criteria:**
1. Given name `shelfie-2`, when scaffolding, then validation passes.
2. Given name `../evil`, `a/b`, `.hidden`, `CON` or an empty string, when scaffolding, then a validation error explains the rule, the exit code is 1 and nothing is written.
3. Given a name of 101 characters, when scaffolding, then a validation error is reported and the exit code is 1.

---

## L2-014: No overwriting without consent
**Traces to:** L1-006

The scaffold shall refuse to write into an existing non-empty target folder unless `--force` is passed. With `--force`, only the files Ezra generates (`AGENTS.md`, `CLAUDE.md` and the copied skill folders) are replaced; other files are left untouched.

**Acceptance Criteria:**
1. Given `shelfie/` exists and contains `notes.txt`, when the user runs `ezra scaffold shelfie --backend node`, then an error states the folder is not empty and suggests `--force`, the exit code is 1 and nothing is changed.
2. Given the same folder, when run with `--force`, then `AGENTS.md`, `CLAUDE.md` and the skills are written and `notes.txt` is unchanged.
3. Given `shelfie/` exists and is empty, when scaffolding without `--force`, then the scaffold succeeds.

---

## L2-015: Safe file copying
**Traces to:** L1-006

When copying skills, Ezra shall not follow symbolic links, shall not write any file whose resolved path falls outside the target project folder, and shall never execute copied files.

**Acceptance Criteria:**
1. Given a skill contains a symbolic link, when scaffolding, then the link is skipped, a warning names it, and its target is not read.
2. Given any write, when its resolved full path is outside the target project folder, then the write is refused and the exit code is 2.
3. Given a skill contains scripts, when scaffolding, then the scripts are copied as files and not executed.

---

## L2-016: Atomic scaffold
**Traces to:** L1-006

A scaffold that fails or is cancelled part-way shall not leave a partially created project behind in a folder that did not exist before the command ran.

**Acceptance Criteria:**
1. Given the target folder did not exist, when a copy fails part-way (for example a source file is unreadable), then the target folder is removed, the error names the failing file and the exit code is 2.
2. Given the target folder did not exist, when the user presses Ctrl+C during the copy, then the target folder is removed and the exit code is 130.

---

## L2-017: Startup and command performance
**Traces to:** L1-007

Commands shall be built so that startup cost does not grow with the number of registered commands: modules shall register commands without performing I/O or network calls, and handlers shall resolve their services only when invoked.

**Acceptance Criteria:**
1. Given Ezra is installed on a CI runner, when `ezra --help` runs 10 times, then the median wall-clock time is under 300 ms.
2. Given a skills source of 50 skills totalling 10 MB, when `ezra scaffold` runs on a CI runner, then it completes in under 2 seconds.
3. Given any command, when it starts, then no network request is made unless that command's purpose requires it.
